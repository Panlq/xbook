# 什么是镜像？

**镜像其实就是一个特殊的文件系统，它提供了容器中程序执行需要的所有文件，就是程序启动需要的三类文件：相关的程序可执行文件，库文件和配置文件。**

**可以通过 docker save 将镜像保存到指定文件**

**docker load 将镜像文件导出为镜像**

```bash
#如下命令表示将本地的nginx:latest镜像和busybox:latest镜像导出到一个名为test.images的文件中，-o参数用于指定导出镜像时输出的文件名
docker save -o test.images nginx:latest busybox:latest
```

我们可以一次性导出一个或多个镜像到一个文件，上例中导出的文件名为 test.images，我们可以把 test.images 文件拷贝到其他 docker 主机上，然后通过 `<span class="ne-text">docker load</span>`命令即可把这个文件中包含的所有镜像导入到其他 docker 主机上

> docker load -i test.images

有了镜像之后就能用如下命令将镜像跑起来

> `docker run -d nginx:latest`

# 什么是容器？

容器的本质：一个视图被隔离、资源受限的进程

## 为什么要隔离？

对于 Linux 操作系统来说，一个不受任何限制的应用程序是十分危险的。这个进程能够看到系统里所有的文件、所有的进程、所有的网络流量，访问内存里的任何数据，那么恶意程序很容易就会把系统搞瘫痪，正常程序也可能会因为无意的 Bug 导致信息泄漏或者其他安全事故。虽然 Linux 提供了用户权限控制，能够限制进程只访问某些资源，但这个机制还是比较薄弱的，和真正的“隔离”需求相差得很远。

**使用容器技术，我们可以让应用程序运行在一个有严密防护的“沙盒”（Sandbox）环境之内** ，就好像是把进程请进了“隔离酒店”，它可以在这个环境里自由活动，但绝不允许“越界”，从而保证了容器外系统的安全。

**容器技术的另一个本领就是为应用程序加上资源隔离，在系统里切分出一部分资源，让它只能使用指定的配额** ，比如只能使用一个 CPU，只能使用 1GB 内存等等，就好像在隔离酒店里保证一日三餐，但想要吃山珍海味那是不行的。这样就可以避免容器内进程的过度系统消耗，充分利用计算机硬件，让有限的资源能够提供稳定可靠的服务。

## 隔离是怎么实现的？

![img](https://learn.lianglianglee.com/%e4%b8%93%e6%a0%8f/%e5%ae%b9%e5%99%a8%e5%ae%9e%e6%88%98%e9%ab%98%e6%89%8b%e8%af%be/assets/5bbf4ac2fa9f81066732yy6f6202b8d2.jpg)

### Linux 常见的 Namespace 隔离技术

| Namespace 类型 | 标识常量 (`CLONE_NEWxxx`) | 隔离内容                                       | 作用描述                                                                                       | 示例                                                 |
| -------------- | ------------------------- | ---------------------------------------------- | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| **Mount**      | `CLONE_NEWNS`             | 挂载点和文件系统结构                           | 每个容器有独立的挂载表，可以拥有不同的根目录（如通过 `chroot`）                                | 容器内看到的是自己的 `/proc`,`/tmp`等目录            |
| **UTS**        | `CLONE_NEWUTS`            | 主机名和域名                                   | 允许每个容器设置独立的主机名（如 `hostname`）                                                  | Docker 容器中运行 `hostname mycontainer`不影响宿主机 |
| **IPC**        | `CLONE_NEWIPC`            | 进程间通信资源（如消息队列、信号量、共享内存） | 容器之间不能直接通过 System V IPC 或 POSIX IPC 通信                                            | 防止不同容器之间的共享内存干扰                       |
| **PID**        | `CLONE_NEWPID`            | 进程 ID 空间                                   | 每个容器有自己的 PID 1（init 进程），进程号从 1 开始分配<br />实际与主机的某个进程 id 一一映射 | 容器中运行 `ps aux`只能看到容器内的进程              |
| **Network**    | `CLONE_NEWNET`            | 网络设备、协议栈、端口等                       | 每个容器有独立的网络栈（IP、端口、路由表等）                                                   | 容器可以绑定到 80 端口而不会与宿主机冲突             |
| **User**       | `CLONE_NEWUSER`           | 用户和组 ID 映射                               | 实现用户权限隔离，允许容器 root 映射为宿主机普通用户                                           | 提高安全性，避免容器逃逸获得宿主机 root 权限         |
| **Cgroup**     | `CLONE_NEWCGROUP`         | 控制组（cgroup）层级                           | 限制容器对资源（CPU、内存等）的访问                                                            | 结合 Cgroups 实现资源配额限制（如内存或 CPU 限制）   |

---

在于 Linux 操作系统内核之中，为资源隔离提供了三种技术： **namespace、cgroup、chroot** ，虽然这三种技术的初衷并不是为了实现容器，但它们三个结合在一起就会发生奇妙的“化学反应”。

namespace 是 2002 年从 Linux 2.4.19 开始出现的，和编程语言里的 namespace 有点类似，它可以创建出独立的文件系统、主机名、进程号、网络等资源空间，相当于给进程盖了一间小板房，这样就实现了系统全局资源和进程局部资源的隔离。

cgroup 是 2008 年从 Linux 2.6.24 开始出现的，它的全称是 Linux Control Group，用来实现对进程的 CPU、内存等资源的优先级和配额限制，相当于给进程的小板房加了一个天花板。

chroot 的历史则要比前面的 namespace、cgroup 要古老得多，早在 1979 年的 UNIX V7 就已经出现了，它可以更改进程的根目录，也就是限制访问文件系统，相当于给进程的小板房铺上了地砖。

# 怎么限制容器的 cpu

以下内容是基于 cgroup v1 的，针对 cgroupv2 驱动的可以看》》》[cgroupv2 特性简析](../../golang/xcgroup/cgroupv2特性简析.md)

首先要了解 k8s cpu 的单位，在 k8s 中，1 核 = 1000ms，0.1 = 100ms

[Kubernetes 中 cpu, mem 的资源单位](https://kubernetes.io/zh-cn/docs/concepts/configuration/manage-resources-containers/#resource-units-in-kubernetes)

在 k8s 的 pod 资源文件种，有两项内容，request cpu 和 limit cpu，对应在 cgroup v1 的中限制，主要有三个参数

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: frontend
spec:
  containers:
  - name: app
    image: images.my-company.example/app:v4
    env:
    resources:
      requests:
        memory: "64Mi"
        cpu: "1"
      limits:
        memory: "128Mi"
        cpu: "2"
…
```

### cpu.cfs_period_us

cpu.cfs_period_us: cfs 算法的一个调度周期，值一般为 100000，单位是 microseconds，也就是 100ms

### cpu.cfs_quota_us

cpu.cfs_quota_us：在表示 cfs 算法种，在一个调度周期里这个控制组被允许的运行时间，比如这儿值为 50000，就是 50ms

如果用这个值去除以调度周期（也就是 cpu.cfs_period_us），50ms/100ms = 0.5，这样这个控制组被允许使用的 CPU 最大配额就是 0.5 个 CPU

上面的 pod 的 cpu.limit 对应到 cpu.cfs_quota_us 就是 200000，相当于 2 个 cpu 时间片，可以说在 1s 的时间里可以占用 0.2s

### cpu.shares

这个值是 CPU Cgroup 对于控制组之间的 CPU 分配比例，它的缺省值是 1024。shares 需要和其他 cgroup 的值进行比较才知道自己的相对限额。

假设 pod1 中的 cpu.shares 是 1024，而 pod2 中的 cpu.shares 是 3072，那么 pod1:pod2=1:3

在一台 4 个 CPU 的机器上，当 pod1 和 pod2 都需要 4 个 CPU 的时候，它们实际分配到的 CPU 分别是这样的：pod1 是 1 个，pod2 是 3 个。

cpu shares 的计算公式

> cpu.shares = (cpu request / 1000) \* 1024

如果 pod2 不忙，pod1 的 cpu 使用率可以超过 1/4，所以是一个软限制，在空闲时，CPU 占用也很容易超过 request 申请的值，因此只能作为 resource.request，不能作为 resource.limits。

# 怎么限制内存

- memory.limit_in_bytes: 一个控制组里所有进程可使用内存的最大值
- memory.oom_control: 当控制组中的进程内存使用达到上限值时，这个参数能够决定会不会触发 OOM Killer，如果没有人为设置的话，memory.oom_control 的缺省值就会触发 OOM Killer。这是一个控制组内的 OOM Killer，和整个系统的 OOM Killer 的功能差不多，差别只是被杀进程的选择范围：控制组内的 OOM Killer 当然只能杀死控制组内的进程，而不能选节点上的其他进程
- memory.usage_in_bytes: 只读参数，记录当前控制组里所有进程实际使用的内存总和，数值越接近 limit_in_bytes，oom 风险越高

Memory Cgroup 中每一个控制组可以为一组进程限制内存使用量，一旦所有进程使用内存的总量达到限制值，缺省情况下，就会触发 OOM Killer。这样一来，控制组里的“某个进程”就会被杀死。

“杀死某个进程"的选择标准(Linux 内核里有一个 **oom_badness()函数** ，就是它定义了选择进程的标准)，控制组中总的可用页面乘以进程的 oom_score_adj，加上进程已经使用的物理内存页面，所得值最大的进程，就会被系统选中杀死

在/proc 文件系统中，每个进程都有一个 /proc/pid/oom_score_adj 的接口文件。我们可以在这个文件中输入-1000 到 1000 之间的任意一个数值，调整进程被 OOM Kill 的几率

# 问题

## 1. 如何理解镜像？

**镜像其实就是一个特殊的文件系统，它提供了容器中程序执行需要的所有文件，就是程序启动需要的三类文件：相关的程序可执行文件，库文件和配置文件。**

## 2. 容器的所有进程调度、内存访问、文件读写都直接跑在主机的内核上，这是怎么做到的？

**Namespace 是一种隔离机制，主要目的是隔离运行在同一宿主机上的容器，让这些容器之间不能访问彼此的资源**

**Namespaceq 起到资源隔离的作用：**

1. **可以充分利用系统的资源，即同一台宿主机上可以运行多个用户的容器**
2. **保证了安全性，不同用户之间无法访问对方的资源**

**cgroups 起到资源限制的作用：**

- **cpu：用来限制一个控制组（一组进程），控制 cpu 数量**
- **memroy ：用来控制一个控制组最大的内存使用量**
- **pids ：用来限制一个控制组最多可以运行多少个进程**
- **cpuset：限制一个控制组的进程可以在那几个 cpu 上运行**

## 3. 计算密集型的作业如何锁死申请的 cpu?

cpuset：限制一个控制组的进程可以在那几个 cpu 上运行，时间片的隔离，可以使用 guaranteed 类型的 resources 定义，

绝对隔离的需要使用 kernal 级别的内核隔离
